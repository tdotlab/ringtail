# RingTail architecture

This is the map: what the parts are, where each one lives, how they talk
to each other, and the rules that keep them working. It is for whoever
opens the code cold, person or agent. It does not repeat the detail:

- README.md, "Design in brief", says how each subsystem behaves (memory,
  interrupts, CPUs, tasks, signals, the filesystem, the network, TLS).
- TODO.md, "House rules" and "Things that bit before", says how work is
  done here and what has gone wrong before. Read it before changing code.
- PROGRESS.md is the history, release by release.
- `src/include/ringtail/abi.h` is the contract between programs and the
  kernel: every system call number, structure and flag.

Each source file opens with a comment that says what it is for and the
rules it keeps. When this map and a file disagree, the file is right;
fix the map.

## Size

As of fa3929a, in lines of C, assembly and Python:

| Part | Lines |
|---|---|
| Kernel (`src/` minus `src/programs`, headers included) | 16,100 |
| Program library (`src/programs/lib`) | 15,700 |
| Programs (`apps`, `files`, `text`, `net`, `util`) | 16,500 |
| Tests written by hand (C, Python, test programs) | 16,600 |
| Test cases generated by scripts (`tests/*_cases.*`) | 70,000 |

So the system is about 48,000 lines, two thirds of it user space, and
with the tests written by hand about 65,000. The tests are part of the
work, not packing around it: most of what RingTail can be trusted to do
is known because a test does it. The generated case tables are expected
outputs recorded from GNU tools, OpenSSL and Wycheproof by the `gen_*`
scripts (which are counted with the hand-written tests); nobody edits
them, so they are left out of the 65,000. Everything in the tree comes to
about 135,000.

## Five ideas the layout follows

**The kernel does mechanism, programs do policy.** The kernel has the
drivers, memory, tasks, the filesystem, and the network up to TCP and the
DHCP client. Everything that can live in ring 3 does: the shell, the
window server and its toolkit, the DNS resolver, SNTP, TLS, X.509 and
signature checking. A bug there costs one program, not the machine, and
it can be tested on the host.

**Cores make no system calls.** The hard part of most things is written
as a core that only computes, and a thin layer joins it to the system.
The core then builds on Linux too, and a host test runs it against a
reference: GNU's tools, dash and bash, OpenSSL, the RFCs' own examples.

| Core | Joined to the system by | Host test |
|---|---|---|
| `programs/lib/shcore.c` (the shell language) | `shos.c` (RingTail) / `tests/shos_host.c` (POSIX) | `test_sh`, against dash and bash |
| `net/tcp.c` (the TCP engine) | `net/tcpsock.c` | `test_tcp`, on a lossy simulated network |
| `programs/lib/tls.c` | three callbacks the caller passes (send, receive, random) | `test_tls`, 218 recorded conversations |
| `programs/lib/x509.c`, `sig.c` | a verifier handed to `tls.c` | `test_x509`, `test_sig` |
| `regex.c`, `diffcore.c`, `pfcore.c`, `splitcore.c`, `joincore.c`, `factorcore.c`, `b64.c`, `shasum.c` | the program of the same job (`grep`, `diff`, `printf`, ...) | `test_regex`, `test_diff`, ... against GNU |
| `wm.c` (window placement, damage) | `apps/pleroma.c` | `test_wm` |
| `tk.c` (the toolkit) | `win.c`, then each window program | `test_tk`, reading back pixels |
| `net/dhcpmsg.c`, `dnsmsg.c`, `ntpmsg.c` | `net/dhcp.c`, `dns.c`, `programs/net/sntp.c` | `test_netmsg`, under ASan and UBSan |
| `fs/diskfs.c` + `mm/heap.c` | `fs/file.c` | `test_heap_diskfs`, on a RAM disk that fails on cue |
| `drivers/ata.c` | the real ports | `test_ata`, a model drive on a model clock (`tests/ata_shim`) |
| `lib/keymap.c`, `lib/vt.c` | the keyboard driver and pleroma; the console and wterm | `test_keymap`, `test_vt` |

When you add something hard, give it this shape.

**One contract.** `src/include/ringtail/abi.h` is the only header both
sides include for the interface. A program reaches the kernel only
through system calls: no program code calls into the kernel, and no
kernel code reads user memory except through the checked copies in
`mm/usermem.c`.

**`src/lib` is shared.** The string routines, the printf subset,
SHA-256, ChaCha20, the calendar, the key map and the terminal emulator
are compiled twice: into the kernel and into `libu.a`. Code there must
work in both, so it uses nothing but itself.

**Machine-specific code lives in `src/arch/x86_64`.** Code that only one
machine needs goes there, not behind an `#ifdef` elsewhere.
`src/include/arch.h` is what the rest of the kernel may ask of a port. The
register frame, the per-CPU block and the FPU state are in
`src/arch/x86_64/include/arch/`.

## Boot

1. GRUB loads `ringtail.bin` as Multiboot 1 and enters `_start` in
   `arch/x86_64/boot.asm` in 32-bit mode. The stub checks for 64-bit
   support, maps the first 4 GB three ways with 2 MB pages, enters long
   mode and jumps to the kernel's linked address at -2 GB.
2. `kernel_main` (`kernel/kernel.c`) brings things up in dependency
   order: GDT and per-CPU block, the kernel lock, serial, the boot info
   (memory map, framebuffer), the console, IDT, FPU, random, then memory
   (heap after the image, frames for the rest, `paging_init`'s real
   tables, the direct map). After that come the interrupt controller
   (ACPI MADT, APICs, or the 8259s), the task system, graphics, the
   banner, mouse, keyboard, timer, the other CPUs (`smp_init`), the
   disk, PCI and the network.
3. `console_start` hands drawing to the console task. Then `init` is
   created and the boot CPU becomes its idle task.
4. `init` (`kernel/init.c`) waits for DHCP (up to five seconds), runs
   `SNTP -b` once if the network is up, then runs `SAKLAS` in the
   foreground and starts a new one whenever it ends.

Each other CPU starts in `arch/x86_64/trampoline.asm`, copied below
1 MB, reaches `ap_main` in `smp.c`, and becomes an idle task of its own.

## A system call, end to end

```
program           ulib.h wrapper → syscall (or int 0x80)
isr.asm           syscall_entry / isr_common: swapgs, save registers into regs_t
interrupt.c       interrupt_dispatch: take the kernel lock, sti, syscall_handle
syscall.c         table[rax](rdi, rsi, rdx) → sys_open, sys_spawn, ...
                  user pointers go through usermem.c; errors are -errno
subsystem         file.c / diskfs.c / net / tty / task.c ... may block
interrupt.c       on the way out: schedule() if needed, deliver pending
                  signals (signal.c, frame built by arch sigframe.c), unlock
isr.asm           sysret (canonical user address) or iretq
```

Every interrupt, exception and system call comes through
`interrupt_dispatch`. It is the one place the kernel lock is taken from
user mode and given back, and signals take effect only there, on the way
back to ring 3, so a signal never lands in the middle of a kernel
operation. Adding a system call means a number in `abi.h`, a `sys_*`
function and a table entry in `syscall.c`, a wrapper in `ulib.h`/`ulib.c`,
and a test program in `tests/programs` driven from `qemu_test.py`.

## Concurrency rules

- **One big kernel lock** (`kernel_lock` in `interrupt.c`). Tasks run in
  ring 3 on every CPU, but only one CPU at a time runs kernel code. A CPU
  takes the lock on the way in and drops it on the way back to ring 3
  or into its idle halt. A CPU's own timer tick needs the lock only to
  switch tasks. Code written for one CPU therefore still excludes
  everything else.
- **Waiting is `task_block(chan)` / `task_wakeup(chan)`** (`task.c`),
  where `chan` is the address of the thing waited on (a pipe, a socket,
  a tty). Wakeups may be spurious, so every waiter looks again after
  waking, with interrupts off between the look and the sleep.
- **Interrupt handlers only record and wake.** The e1000 handler wakes
  the `net` task, which does the work under `net_lock`. The keyboard and
  serial handlers feed the tty and wake its readers. `task_wakeup` is
  safe from an interrupt handler.
- **Sleeping locks** (`sync.h`) guard what can block halfway through:
  `fs_lock` (diskfs), `net_lock` (the whole network stack), the
  console's locks, a tty's handover and output locks, and each open
  file's offset. They are recursive, and they are never taken in an
  interrupt handler.
- **Only a task changes its own descriptor table and signal actions.**
  Others may set its `sig_pending`, which changes only by atomic
  operations.
- **Device interrupts all go to the boot CPU.**

The bugs that hide from QEMU, and why, are listed in TODO.md, "Things
that bit before". A green run does not prove interrupt routing or
locking is right.

## Memory

The layout is in `src/include/mm.h`. In short:

| Range | What |
|---|---|
| below 1 GB | nothing mapped, so a null pointer faults in the kernel too |
| 1 GB `USER_BASE` | the program's image (`user.ld` links at 0x40000000), then its break (`sbrk`) |
| 2 GB `SHM_BASE` | shared memory mappings |
| up to 3 GB `USER_TOP` | the stack, growing down on demand to 1 MB, with a guard gap below |
| 3 GB | the device window (the e1000's registers), supervisor only |
| `0xFFFF800000000000` `DIRECT_MAP` | all of RAM, up to 512 GB, never executable |
| -2 GB `KERNEL_VMA` | the kernel image, code read-only and only code executable |

The upper half is the same in every address space. A physical address is
never a pointer: go through `phys_to_virt`. Frames are handed out from
the top of RAM down and zeroed when handed out.

## How things flow

**Starting a program.** `sys_spawn` → `loader_spawn` (`kernel/loader.c`)
reads a static ELF from the disk through diskfs, checks every header
field, maps the segments with their own permissions into a fresh address
space, and builds the stack `crt0.c` expects. The child's descriptors 0
to 2 are its parent's 0 to 2, or the ones the spawn options name, plus an
optional fourth (`SPAWN_FD3`). They are the same open files, with a
shared offset (`file.c`). It also gets its parent's directory and terminal.
`SPAWN_FOREGROUND` gives it the terminal before its first instruction.
There is no `fork`.

**A key press.** The keyboard interrupt (`drivers/keyboard.c`) turns the
scancode into a key with `lib/keymap.c` and gives it to the console's tty
(`drivers/tty.c`). The tty does the line editing and Ctrl+C/Ctrl+\, and
wakes the foreground job's reader. While a program owns the display
(`gfx.c`), raw scancodes go to it through `sys_key_get` instead. Serial
input (`serial.c`) feeds the same tty. In a terminal window, wterm writes
the keys into a pty's master side, and the pty's tty treats them the
same way.

**Output.** A write to a terminal descriptor goes through `file.c` to the
tty and on to `console_write`. The console (`console.c`) updates its grid
of cells through `lib/vt.c` and mirrors the bytes to serial, and on a
framebuffer the `console` task redraws only the changed cells. A pty's
output goes to a ring that its master (wterm) reads and draws with the
same `vt.c`.

**A file.** `sys_open` / `read` / `write` → `fs/file.c` (descriptor →
open file, data through a kernel bounce buffer) → `fs/diskfs.c` (FAT16
with long names; FAT and root kept in memory; every operation committed
data first, then FAT, then directories) → `drivers/ata.c` (polled PIO,
timed waits, resets and retries). `sys_save` writes a whole file in one
call.

**A packet.** The e1000 interrupt wakes the `net` task (`net/net.c`).
Under `net_lock` the task takes frames off the ring and handles Ethernet,
ARP, IPv4 and ICMP, then hands datagrams to `udp.c`, segments to the TCP
engine through `tcpsock.c`, and DHCP replies to `dhcp.c`. It also runs
the DHCP and TCP timers. A task waiting on a socket sleeps on that
socket and is woken once the engine has finished with the segment.
Loopback goes round through the same task without touching the card.
DNS, SNTP and TLS are user code over these sockets.

**A window.** A client (`win.c`) makes shared memory for its pixels
(`sys_shm_new`), connects to the `pleroma` channel (`sys_chan_connect`)
and sends `wsys.h` messages: hello, create, "this rectangle changed".
pleroma owns the display. It maps the client's pixels, composes the
windows with `wm.c`, and writes the changed parts to the screen with
`sys_gfx_put`. It reads the keyboard and mouse itself (`sys_key_get`,
`sys_mouse_state`, woken by `sys_pollfd` with `POLLFD_INPUT`) and sends
each event to the window it belongs to. Toolkit programs (`kenoma`,
`wfiles`, `wprefs`) turn those events into clicks, keys and menu choices
with `tk.c`. pleroma never waits on a client: a full queue drops events.

## Programs and the library

Every `.c` file one folder down in `src/programs` is a program: `apps`
(the big interactive ones), `files`, `text`, `net` and `util`. The
Makefile finds them, so a new program is a new file. The one exception
is `barb`, several files from `vendor/barb` (a copy of the barb
repository's portable core and its RingTail platform), which the
Makefile links into one program; change it in the barb repository and
copy it over with that repository's `tools/to_ringtail.sh`. Its core
includes `<string.h>`, which `vendor/barb/include` points at `lib.h`. Each one links
statically against `crt0.o` and `libu.a`, an archive, so a program pulls
in only the parts it uses. Programs go flat into the root of the disk
under their names in capitals, so a name is at most 8 characters and
must be unique across all the folders (the Makefile refuses
duplicates). `SH` is a second copy of saklas, for scripts.

`ulib.h` is the system call layer: each wrapper returns what the kernel
returns, a result or `-errno`. Everything else in `programs/lib` is
either a core (above) or glue for one family of programs. `lineio`
buffers the text tools' input and output, `dns` and `dial` look up
names and connect, `win` and `desk` serve the desktop programs, and
`shos` runs the shell on RingTail.

## Building and testing

`make` builds everything into `build/x86_64/`:

- `k/` holds the kernel objects and `ringtail.bin`;
- `u/` holds the library objects and `libu.a`;
- `programs/` and `test-programs/` hold the binaries;
- `disk.img` is the disk you boot, and `test-disk.img` adds `tests/programs`;
- `ringtail.iso` and `ringtail-text.iso` are the bootable images, the
  second forcing VGA text so the fallback stays tested;
- `gen/timefloor.h` holds the build's commit time, below which the
  kernel refuses to set its clock.

`make test` runs `tests/Makefile` (the host tests, about twenty of
them), then `tests/qemu_test.py`. That suite boots the real ISO on two
CPUs, drives the shell over a serial socket, reads the screen back
through the QEMU monitor, and runs the network checks against host-side
peers. The full run takes about ten minutes.

Generated cases come from `tests/gen_*.py`, which run the real reference
(GNU tools, dash and bash, OpenSSL, Python's `cryptography`) and write
`*_cases.h` or `text_cases.py`. To change what is expected, change the
generator and run it again; never edit the output.

## Known edges

These are the limits that shape the architecture. README's "Limits"
lists the rest.

- One CPU at a time in the kernel (the big lock). Splitting it is
  in TODO.md, "SMP, past the big lock".
- Every device interrupt goes to the boot CPU, and PCI interrupts come
  from the line register, since there is no AML to read `_PRT`. This is
  right on QEMU but not on every real board.
- One disk, polled, FAT16. The e1000 is the only network card.
- `spawn` instead of `fork`/`exec`. There is no job control and no
  environment for programs.
- One program owns the display at a time. Under pleroma that program is
  pleroma.
- Everything has been run under QEMU. Real hardware is untested.
